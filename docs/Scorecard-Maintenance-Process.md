# Phase 1 Scorecard — Maintenance Process

**Status:** Active process reference. Supersedes
`docs/Scorecard-Single-Source-Implementation-Plan.md` (that file was the
draft plan for *building* this system; this file is how the finished
system is actually kept correct day to day).

## The picture

There is one ledger and two photocopies.

- The ledger is `docs/Signed-Requirements-to-PRD-Traceability.md`. It is
  the only file anyone hand-edits a delivery status in.
- The photocopies are `docs/Phase1-Delivery-Scorecard.md` (internal) and
  `.scratch/phase1-scorecard.html` (the published client-facing Artifact).
  Both are generated from the ledger by `scripts/generate_scorecard.py`
  and are never hand-edited.
- The ledger's own summary line ("Current tally: X Done · Y Partial · Z
  Not started") is also generated by that script, not hand-typed — it
  lives between `<!-- TALLY:START -->` / `<!-- TALLY:END -->` markers in
  the ledger file itself, so it can never silently drift from the table
  above it the way it once did (caught 2026-09-16: header said 26/14, the
  real row count was 27/13).

## The lifecycle

1. **Build the feature.** Ordinary development work, unchanged.
2. **Test it fully.** A row may only move to **Done** once the feature's
   complete manual E2E test plan has been checked off — not on "code
   merged" or "smoke-tested." Until then the row stays Partial or Not
   started, with an honest Note on what's still outstanding, even if the
   code is already live. (Example: Report Drill-down, Feature 11.2 —
   built and committed 2026-09-15, still correctly shown Partial because
   its full E2E pass hasn't run yet.)
3. **Flip the status and propagate it as one step.** The moment a row is
   ready to change, do both of these together, not the first now and the
   second "later":
   - Edit the Status / Notes / Client Note cells in the ledger.
   - Run `python scripts/generate_scorecard.py` — this rewrites the
     ledger's own tally line and regenerates both photocopies from the
     updated table.
4. **Verify before committing.** Run
   `python scripts/generate_scorecard.py --check` — read-only, compares
   what the ledger currently computes to against what's actually on disk
   in all three files, and exits non-zero naming whichever file(s) are
   stale. Treat a non-zero exit as a blocker, not a warning.
5. **Republish if client-visible.** If the change affects what
   Haroon/Latheef Bhai see, republish `.scratch/phase1-scorecard.html` to
   its Artifact URL so the live page matches the ledger.

## Quick reference

| File | Role | Edited how |
| :--- | :--- | :--- |
| `docs/Signed-Requirements-to-PRD-Traceability.md` | Source of truth | Hand-edit Status/Notes/Client Note cells only. Never hand-edit the tally line between the TALLY markers. |
| `docs/Phase1-Delivery-Scorecard.md` | Internal scorecard | Generated only — never hand-edit. |
| `.scratch/phase1-scorecard.html` | Client-facing Artifact | Generated only — never hand-edit. Republish after regenerating. |
| `scripts/generate_scorecard.py` | The generator | `(no flag)` writes all three outputs. `--check` verifies without writing, exit 1 if stale. |

This process is also codified as a standing rule in `CLAUDE.md`'s
`## Scorecard integrity` section, so it applies automatically in every
future session rather than depending on anyone remembering it.
